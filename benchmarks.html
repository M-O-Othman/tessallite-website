Methodology scaffold

Benchmark-style proof for governed acceleration on BigQuery.

Tessallite is preparing a public benchmark page for a TPC-DS-derived SF1000 retail analytics workload on BigQuery. The evidence capture is not complete yet, so this page documents the methodology, planned charts, publication criteria, and proof points before any numbers are published.

This is not an official TPC audited result. It does not include third-party benchmark branding, and the page will not claim audited standing, market ranking, or broad performance superiority. The benchmark will show a repeatable Tessallite methodology against a governed source baseline.

Methodology

A defensible benchmark starts with conditions, not headlines.

The benchmark will measure a curated set of buyer-relevant analytical questions mapped to a semantic model, direct BigQuery baselines, and Tessallite source, aggregate, and pocket routes.

Workload and source

The planned data source is a TPC-DS-derived SF1000 retail analytics dataset loaded into BigQuery. BigQuery remains the source execution engine; Tessallite provides governed modelling, protocol access, route selection, and transparent acceleration.

Run discipline

Published runs will identify cache policy, compute model, BigQuery region, query count, run count, warmup discard policy, Tessallite version, model version, and seeded acceleration state.

Correctness first

Each accelerated answer must compare back to the BigQuery source baseline using explicit numeric tolerance, ordering rules, checksums or row evidence, and documented exclusions for queries that do not map cleanly.

Result cache, BI Engine, and BigQuery materialized views are real BigQuery capabilities. The benchmark will describe them accurately and position Tessallite as semantic-model-aware, workload-suggested, version-aware, and multi-protocol acceleration rather than as a replacement for BigQuery.

What will be measured

Evidence will cover latency, cost drivers, route behavior, and operating effort.

No performance values are shown until the benchmark runner emits raw evidence and chart-ready data.

Runtime metrics

  • P50 and P95 elapsed latency by route.
  • Bytes processed and cache-hit status.
  • Slot-ms where available from BigQuery jobs.
  • Variance across repeated uncached runs.

Route and acceleration metrics

  • Direct BigQuery SQL baseline.
  • Tessallite source route through the gateway.
  • Aggregate route hits and selected aggregate IDs.
  • Pocket route hits, freshness, and selected pocket IDs.

Human effort and serviceability

  • Manual DDL lines and physical objects maintained.
  • Time-to-first-accelerated-answer.
  • Protocols served from one governed definition.
  • Change failure mode when source or model shape moves.

Named sets, aggregates, and pockets

The benchmark story is governed acceleration, not isolated SQL timing.

The planned demo flow shows the same governed question moving through source, aggregate, and pocket routes while named sets keep business filters reusable across agent, Excel, BI, and API access.

1

Source baseline

Curated questions execute against BigQuery through the governed source route, with correctness evidence captured first.

2

Aggregate route

Recurring analytical patterns route to maintained aggregates seeded from the semantic model and reported with route explanations.

3

Pocket route

Exact executive dashboards, such as CFO weekly revenue, can route to pockets with freshness metadata and lineage visible.

4

Named sets

Saved business lists, such as high-value customers or strategic categories, are governed objects rather than copied spreadsheet filters.

Evidence publication

The public page and PDF brief will be populated from evidence, not estimates.

The runner still needs to publish raw JSON evidence, chart data, methodology metadata, correctness checks, and screenshots before public benchmark values can appear.

Evidence to publish

  • Raw run records with query ID, run ID, route, elapsed time, bytes processed, cache-hit flag, and BigQuery job reference.
  • Correctness comparison against the BigQuery source baseline, including tolerance, ordering rule, checksum, and exclusion reason where needed.
  • Aggregate and pocket identifiers, refresh time, route explanation, and freshness metadata.
  • Chart-ready summaries for latency, bytes processed, route mix, convergence, and manual effort.
  • Benchmark environment metadata: date, region, compute model, version, model version, cache mode, query count, and run count.
